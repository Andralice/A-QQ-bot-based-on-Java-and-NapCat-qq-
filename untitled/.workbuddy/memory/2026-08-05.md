## 排障：三角洲截图功能全部失效（已定位根因）

### 现象
群里发「特勤处」「脑机」「密码」→ 机器人回 `❌ XX截图失败：Failed to take screenshot for task: kkrb-overview-X`。

### 根因（已闭环验证）
运行中的 JAR（`/opt/qq-bot/untitled-1.0-SNAPSHOT.jar`，2026-07-29 17:39 编译）里的
`WebScreenshotService.class` **不包含 `PLAYWRIGHT_BROWSERS_PATH` 设置**（用
`unzip -p ... | strings | grep -i playwright` 验证为空）。

Java 进程以 **root** 身份运行 → Playwright 回退到默认路径
`$HOME/.cache/ms-playwright` = `/root/.cache/ms-playwright` → **该目录不存在**。
浏览器实际装在 `/home/alice/.cache/ms-playwright/`（chromium-1200 /
chromium_headless_shell-1200 / ffmpeg-1011，属 alice）。

报错：`BrowserType.launch: Executable doesn't exist at
/root/.cache/ms-playwright/chromium_headless_shell-1200/chrome-headless-shell-linux64/chrome-headless-shell`

### 关键定位手法（可复用）
1. 日志时间差是最强信号：`14:06:31.805` 收到「密码」→ `14:06:32.329` 报失败，
   仅 **524ms**；而脚本正常执行需 **5.5s** → 判定 Python 进程"根本没跑起来"，
   而非网站/选择器问题。
2. `SanjiaoHandler.exceptionally` 只取 `ex.getCause().getMessage()`，
   真实 cause 在第 3 层被吞掉 → 日志里看不到真因。
3. 绕过日志直接复现：`javac -cp <jar>` 写 T2.java 调用 JAR 里的**真实类**
   `new WebScreenshotService().takeScreenshot(task).join()`，循环打印 cause 链
   → 一次性拿到被吞掉的第 3 层异常。
4. 用 `/proc/<pid>/environ` 还原 Java 进程真实环境变量做精确复现对照。

## 部署完成（14:37）——「根治」方案已落地，截图功能已恢复

### 关键坑：本地打不了包，必须在服务器构建
本地 Windows 只有 **JDK 1.8**（`C:\Program Files\Java\jre1.8.0_291`），
而 `pom.xml` 要求 `maven.compiler.source/target = 17` → **`deploy.sh` 的第 1 步 `mvn package` 在本地必然失败**。
服务器有 `openjdk 17.0.19` + `/usr/bin/mvn`，所以改为**服务器侧构建**：

```bash
# 1. 本地打包源码（排除 58M 的 assets，只有 345K）
tar czf /tmp/qqbot-src-sync.tar.gz --exclude='src/main/resources/assets' src pom.xml
scp /tmp/qqbot-src-sync.tar.gz root@154.8.213.134:/opt/qq-bot/

# 2. 服务器解压时保住 assets（先挪走再挪回）
cd /opt/qq-bot/untitled
cp -r src/main/resources/assets /tmp/_assets_keep
rm -rf src pom.xml && tar xzf /opt/qq-bot/qqbot-src-sync.tar.gz -C .
mv /tmp/_assets_keep src/main/resources/assets

# 3. 离线构建（-o 走本地 .m2，避免网络）
mvn clean package -DskipTests -q -o

# 4. 备份 + 替换 + 同步 py 脚本
cp untitled-1.0-SNAPSHOT.jar untitled-1.0-SNAPSHOT.jar.bak.$(date +%Y%m%d_%H%M%S)
ls -t untitled-1.0-SNAPSHOT.jar.bak.* | tail -n +4 | xargs -r rm -f
cp untitled/target/untitled-1.0-SNAPSHOT.jar untitled-1.0-SNAPSHOT.jar
cp untitled/src/main/resources/{screenshot.py,edge_tts.py} /opt/qq-bot/

# 5. screen 启动
screen -S qq-bot -d -m bash -c "source /opt/qq-bot/.env; exec java -Xms256m -Xmx768m -jar /opt/qq-bot/untitled-1.0-SNAPSHOT.jar >> /opt/qq-bot/qq-bot.log 2>&1"
```

### 踩到的两个小坑
1. **`pkill -f "java.*untitled-1.0-SNAPSHOT.jar"` 会自杀** —— SSH 执行的 bash 命令行本身包含该字符串，
   被 pgrep/pkill 匹配到，导致 SSH 退出码 255、`pgrep` 返回一个假 PID。
   验残留要用 `ps -eo pid,cmd | grep "^ *[0-9]* java"`。
2. **测试截图要传 task key 不是 label** —— `screenshot.py` 的 `TASKS` 字典键是
   `kkrb-overview` / `kkrb-overview-2` / `kkrb-overview-3`，「特勤处」只是 `label` 字段值。
   传 label 会得到 `ERROR: Unknown task`（324ms 秒失败）。

## 根治措施（15:42）—— journald 上限 + qq-bot logrotate（用户「做吧」）

### journald 上限
- 备份 `/etc/systemd/journald.conf.bak.<ts>`
- 设 `SystemMaxUse=200M`、`SystemKeepFree=100M`
- `systemctl restart systemd-journald` → active（fallback 备 `kill -USR1 $(pidof systemd-journald)`）

### qq-bot.log logrotate
- 新增 `/etc/logrotate.d/qq-bot`：size 100M / rotate 5 / compress / delaycompress / **copytruncate**
- `copytruncate` 关键：进程持有文件句柄，避免默认 `mv` 重建导致日志写丢 + 磁盘不释放
- `logrotate -d` 语法 OK；`logrotate -f` 强制验证：qq-bot.log 截断为 0、轮出 `.1`(132K)，进程 PID 3812294 仍存活 → 方案安全

### 现状
- 磁盘不再会被日志撑爆（journald 200M 上限 + qq-bot.log 100M 自动轮转）
- 未减量根因：DEBUG 打印 OneBot 全量事件仅被 logrotate 防撑爆，未减少量；根减需调日志级别并重新部署，用户未要求
